# PickleIQ — Architecture Overview

**Status:** Approved  
**Last updated:** 2026-05-31

This document records the technology decisions for PickleIQ Phase 1. Each decision is explained with rationale and alternatives considered.

---

## Decision 1 — UI Layer: Blazor Server

PickleIQ uses **Blazor Server** for the web frontend. Blazor Server runs on the server and pushes UI updates to the browser over a persistent SignalR connection. This gives us real-time video processing status updates without a separate polling API, no JavaScript build pipeline to maintain, and a single .NET technology stack across the entire application. The team's existing .NET expertise applies directly to frontend work.

**Alternatives considered:**

| Alternative | Reason not chosen |
|-------------|------------------|
| React + ASP.NET Core API | Adds a separate build pipeline and requires JavaScript/TypeScript expertise for a team focused on .NET |
| Razor Pages | No real-time capability; would require polling via JavaScript for job status updates |
| Blazor WebAssembly | Requires API layer for all data access; no advantage over Blazor Server for this app type |

---

## Decision 2 — Video Processing: FFmpeg via FFMpegCore

All video operations — frame extraction, clip trimming, and highlight concatenation — use **FFmpeg** through the **FFMpegCore** .NET wrapper. FFmpeg is the industry standard for video processing, runs locally with no API costs, and handles the full range of MP4 encoding and decoding scenarios. FFMpegCore provides a fluent .NET API over the FFmpeg CLI.

**Alternatives considered:**

| Alternative | Reason not chosen |
|-------------|------------------|
| Azure Media Services | Cloud cost per minute of processed video; overkill for MVP; adds external dependency |
| Mux | SaaS pricing model conflicts with self-hosted, free-tier goal |
| MediaToolkit | Unmaintained; FFMpegCore is the maintained community standard |

**Licensing note:** FFmpeg is LGPL-licensed. See R08 in the Risk Register for compliance notes on binary distribution.

## Decision 3 — Computer Vision: YoloDotNet with Pre-Trained YOLO Models

Player and court detection use **YoloDotNet**, a .NET library that runs YOLO inference locally. Pre-trained YOLO models (trained on the COCO dataset, which includes "person" detection) are used for Phase 1. No external API calls are required; all inference runs on the local machine.

YOLO models are distributed as `.onnx` files. YoloDotNet handles loading and running them via ONNX Runtime internally — this is an implementation detail that developers do not interact with directly.

**Alternatives considered:**

| Alternative | Reason not chosen |
|-------------|------------------|
| Azure Computer Vision | Per-call API cost; data leaves the server |
| Roboflow | Cloud-hosted inference; adds latency and cost |
| Custom-trained YOLO model | Phase 1 uses pre-trained; custom training planned for Phase 3 if accuracy < threshold |

**Known limitation:** Pre-trained YOLO "person" detection was not trained on pickleball courts. Accuracy may vary with court lighting and camera angle. See R04 in the Risk Register.

---

## Decision 4 — AI Coaching Engine: Ollama + Nemotron3 (Swappable)

The AI coaching report is generated by a large language model. The **recommended default** is **Ollama** running **Nemotron3** locally. Ollama is a local LLM server that runs open-weight models on the host machine. No data leaves the server, there are no per-token costs, and the model runs entirely offline.

The coaching engine is abstracted behind an `ICoachingEngine` interface. Switching to a different model or provider requires only a configuration change in `appsettings.json` — no code changes.

**Alternative engines (documented and supported via config swap):**

| Engine | Trade-off |
|--------|-----------|
| Ollama + Nemotron3 *(default)* | Free, local, private. Requires local GPU/CPU for inference. |
| Claude API (claude-sonnet-4-6) | Higher reasoning quality. Per-token cost (~$3/MTok input). Requires Anthropic API key. |
| OpenAI API (gpt-4o) | Highest capability option. Per-token cost. Requires OpenAI API key. |

---

## Decision 5 — Data Storage: SQL Server Express

**SQL Server Express** is used for all persistence. It is free, locally hosted, and fully compatible with SQL Server Standard and Enterprise. When PickleIQ scales to the Academy edition, there is no migration cost — the schema and EF Core migrations work unchanged against a paid SQL Server instance.

EF Core is used as the ORM with code-first migrations.

**Alternatives considered:**

| Alternative | Reason not chosen |
|-------------|------------------|
| SQLite | Zero-ops appeal, but limited concurrency and no clear upgrade path for multi-coach Academy edition |
| PostgreSQL | Strong option, but SQL Server Express gives identical upgrade path to enterprise SQL Server |
| Azure SQL | Cloud cost; self-hosted goal for Phase 1 |

---

## Decision 6 — Background Processing: Hangfire

Long-running video jobs (frame extraction, detection, highlight generation, report generation) run as **Hangfire** background jobs. Hangfire provides a persistent job queue backed by SQL Server, a built-in dashboard at `/hangfire` for monitoring, automatic retry on failure, and job status tracking.

**Alternatives considered:**

| Alternative | Reason not chosen |
|-------------|------------------|
| ASP.NET Hosted Services | No persistence — jobs lost on app restart; no dashboard |
| Azure Service Bus | Cloud dependency; overkill for single-server MVP |
| Quartz.NET | Scheduler-focused; Hangfire is simpler for fire-and-forget job queuing |

## System Architecture Diagram

```
Browser
  │
  ▼
Blazor Server (PickleIQ.Web)
  │  ├── /upload     → VideoStorageService → Hangfire queue
  │  └── /results    → Poll VideoJob status → Render report
  │
ASP.NET Core (PickleIQ.Api)
  │  └── GET /api/download/{jobId}/highlights → FileStreamResult
  │
Hangfire Worker
  │  └── VideoProcessingJob
  │        ├── Step 1: RallyDetectionService  (FFMpegCore + YoloDotNet)
  │        ├── Step 2: HighlightGenerationService (FFMpegCore)
  │        └── Step 3: CoachingReportGenerator (ICoachingEngine → Ollama)
  │
SQL Server Express
  │  ├── VideoJobs
  │  ├── RallySegments
  │  └── CoachingReports
  │
Local File System
     ├── /videos/{jobId}.mp4      (uploaded source)
     └── /highlights/{jobId}.mp4  (generated output)
```
